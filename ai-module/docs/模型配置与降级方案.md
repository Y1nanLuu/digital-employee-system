# 模型配置与降级方案（字段提取模块）

> 成员6 · AI与知识检索线 · D1 记录。对应看板交付：记录模型配置、输出格式和不可用时的降级方案。
> 关联代码：`extractor.py`、`model_config.json`；验证：`test_extractor.py`（17/17 通过）、`demo.py`。

## 1. 模型配置（model_config.json，三通道）

通过 `active` 字段切换模型通道，`extractor.py` 与调用方零改动：

| active 值 | 通道 | 说明 |
|---|---|---|
| `local_qwen`（当前） | 本地 Qwen | 本机 HF 缓存 Qwen1.5-0.5B-Chat，llm_server.py 包装为 OpenAI 兼容接口（127.0.0.1:8010），CPU 离线推理 |
| `deepseek` | 远程 API | DeepSeek OpenAI 兼容接口；密钥经环境变量 `DEEPSEEK_API_KEY` 注入（`api_key: "ENV:DEEPSEEK_API_KEY"`），**禁止写入文件**（PRD 4.2）；未配置密钥时自动降级并留 `llm_api_key_missing` 事件 |
| `rule` | 纯规则 | 计划内禁用 LLM 的基线模式，不记降级事件（PRD FR03：须明确标记，不作为真实模型验收证据） |

通用约定：
- `timeout_seconds`：默认且上限 120 秒（PRD FR03），超时降级，不自动重试；
- `temperature`：提取任务固定 0；
- `providers` 内新增其他 OpenAI 兼容服务只需加一项并切换 `active`；
- 旧版扁平格式仍兼容（`load_config` 自动识别）。

**真实调用环境（D2 实测）**：本地 Qwen 通道单次约 15~17 秒（CPU）；deepseek 通道在密钥缺失时实测触发 `llm_api_key_missing` 降级；rule 通道实测正常。项目 venv（`.venv`）内已修正 `huggingface_hub`/`tokenizers` 版本以兼容 transformers 5.8.1。

## 2. 输出格式（字段契约）

LLM 与规则两条路径输出**同构 JSON**，下游初审模块无感知切换：

```json
{
  "submitter": "张伟",
  "department": "研发部",
  "expense_type": "差旅",
  "amount": 3275.0,
  "expense_date": "2026-10-12",
  "invoice_no": "26310100001234567890",
  "invoice_title": "北京中兴协力科技有限公司",
  "description": "赴上海客户现场部署与验收"
}
```

提取结果外层统一包装：`{fields, missing_fields, source: "llm"|"rule", model, fallback_event}`。

## 3. 降级方案

### 触发条件（任一命中即整体降级到规则提取）

| 触发码 | 场景 |
|---|---|
| `llm_timeout_or_unreachable` | 连接超时/服务不可达（demo 已实测） |
| `llm_http_4xx/5xx` | 服务端错误（鉴权失败、限流等） |
| `llm_response_not_json` | HTTP 响应不是合法 JSON |
| `llm_output_not_valid_json` | 模型输出解析失败（含容忍 ```json 围栏后仍失败） |
| `llm_output_not_object` | 输出不是 JSON 对象/数组包裹多对象 |
| `llm_output_unknown_fields:[...]` | 输出含契约外字段（Schema 校验拒绝） |
| `llm_amount_not_numeric` | 金额字段无法转数值 |
| `unexpected:<异常名>` | 未预期异常，兜底降级保证链路不中断 |

### 字段级仲裁（介于"全成功"与"整体降级"之间）

整输出合法但个别字段不可靠时，不废弃整次 LLM 调用，而是逐字段仲裁（`merge_with_rule`）：

- **解析容错**（字段保留）：```json 围栏剥离、`[{...}]` 单对象数组解包、金额字符串去货币符号/千分位、日期区间取起始日；
- **泄漏检测**：few-shot 示例使用哨兵值（"示例公司"、99.9 等），模型照抄哨兵值即判定该字段不可信（D1 实测 0.5B 模型高频发生）；
- **仲裁规则**：不可信/缺失字段 → 规则提取结果补齐（记入 `patched_fields`，demo 表格可见）；**泄漏且规则亦无法补齐 → 字段清空**，宁可缺失走补件流程，避免哨兵值或幻觉值被误作为真实数据传递至下游；
- 结果外层新增 `patched_fields` 字段，与 `fallback_event`（整体降级）区分。

### 降级行为与留痕

- 行为：整体降级时自动切换 `RuleExtractor`（正则 + 键值对解析），**提取能力不降级为空**，实测全部样例降级后仍可提取；
- 留痕：`fallback_event` 结构如下，供工具调用日志（功能要求第 3 条）与管理台展示消费：

```json
{
  "timestamp": "2026-11-05T16:18:15",
  "trigger": "llm_timeout_or_unreachable",
  "llm_model": "demo-model",
  "fallback_to": "rule"
}
```

- 边界：降级事件只记录原因码与时间，**不记录报销单原文**（隐私最小化）。

## 4. D1 验证结论（真实模型调用）

- **真实调用已验证**：Qwen1.5-0.5B-Chat（本机 CPU、离线缓存），单次 14~17s；
- demo 结果：**5/5 样例走 LLM 路径**，金额全部正确（3275.0/6820.5/286.0/70/1280.0），其中样例5 完全由 LLM 提取无仲裁，样例1~4 个别字段经仲裁补齐（明细见 demo 表格），样例4 发票字段按"宁可缺失"清空（餐补无发票，语义正确）；
- 整体降级路径：不可达场景实测留痕正常；
- 测试：`python test_extractor.py` → **17/17 passed**。

### D1 缺陷案例（候选《产品缺陷处理案例》素材）

| # | 现象 | 根因 | 处置 |
|---|---|---|---|
| 1 | 样例5 金额输出 3275.0（真实 1280.0） | few-shot 示例值泄漏：模型照抄示例金额，静默错值 | 示例改哨兵值 + 泄漏检测 + 字段级仲裁 |
| 2 | 样例4 无发票信息却输出 8 字段 | 同上泄漏（发票号/抬头为示例值）且规则无法补齐 | 仲裁时清空该字段，宁可缺失不可错值 |
| 3 | 输出被 `[{...}]` 包裹 / 金额带 ¥ / 日期输出区间 | 0.5B 模型指令遵循能力有限 | 解析器结构化容错（解包/去符/取起始日） |

## 5. 已知衔接点（D2 处理，已登记）

**餐补类无需发票**：制度 DAY-002 规定加班餐补无需发票，而 INV-003 的字段完整性检查将 `invoice_no/invoice_title` 列为必填。D1 终态下样例4 正确显示这两个字段缺失（LLM 泄漏被仲裁清空，规则亦无来源）。这不是提取 bug，是**字段契约需按费用类型差异化**（餐补：发票字段免填，必填打卡记录）。D2 实现初审规则时按 `expense_type` 区分必填字段集；该条已作为制度衔接问题同步产品经理，候选录入《产品缺陷管理清单》。

**0.5B 模型能力边界**：单次调用 14~17s（CPU），`invoice_title/description` 等自由文本字段泄漏率高，依赖字段级仲裁兜底。若团队后续提供 API 沙盒或更大本地模型，`model_config.json` 改三处即可切换，仲裁机制始终保留——对任何模型均为安全网。
