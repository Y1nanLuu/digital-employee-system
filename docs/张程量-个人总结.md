# 面向中小企业的数字员工系统设计与实现——个人总结

## 一、项目背景与我的职责

本次实训的目标是在六个工作日内，为中小企业费用报销初审场景做出一套可运行、可解释、可追溯的数字员工系统。员工提交报销后，系统要完成字段理解、制度检索、预算查询、自动初审或转人工、审批续跑、结果写回、日志与指标展示。与一般表单系统的差别在于：系统不仅要把数据存下来，还要让每一步判断都能被追问“为什么”，并且在信息不足、金额超限、模型不可用或制度没有依据时安全地停下来。

我在团队中担任架构与集成负责人，负责架构设计、数据模型、接口约定、集成与部署，同时也是周勃的后端备份、卢亦楠的发布协调备份。具体到每一天的任务编号：D1-02 建立仓库骨架与架构、数据、接口约定；D2-02 集成前后端、AI 与模拟财务服务并补齐初始化配置；D3-02 集成完整流程并检查状态转换、账号权限和重启恢复；D4-02 修复集成问题、完善 Compose 与部署说明；D5-02 发布候选版本、配合独立部署、核对架构与数据库文档并撰写本总结。此外我在 D4 承担了模型通道联调，并在 D5 完成了 Docker/PostgreSQL 的容器化验证。

## 二、对需求与范围的理解

产品给出的口径很明确：单场景、费用报销初审，金额区间为大于 0 且不超过 5000 元、最多两位小数；1000 元以内且制度与预算都满足时可自动初审，超过 1000 元、缺少适用依据或模型处理异常时转人工；预算不足优先拒绝；审批通过要重新校验字段、重检依据并重查预算；拒绝同样要写回记录。系统还必须支持字段补正并保留原值、新值、理由和操作者，任务编号要贯穿页面、数据库、日志、审批与模拟财务凭证。

同样明确的是范围外事项：OCR、发票验真、真实财务集成、付款或预算扣减、多企业租户、多级组织审批、分页与推送、自动重试调度。我在做架构时把这条边界当作硬约束：凡是范围外的能力，不做“看起来像做了”的实现，而是在文档与页面上显式声明。例如发票识别这一项，我后来追加的只是带文字层 PDF 的文本抽取，它并不是 OCR，也没有任何验真能力，这一点我在部署文档与集成文档里都写清了。

## 三、架构设计与技术取舍

系统分四层：接入层是 Vue 3 + TypeScript 工作台，只经 `/api` 访问后端；治理层是 FastAPI 业务服务，负责鉴权、任务状态机、审批与指标；认知层是 `ai.py` 适配层加 `ai-module`，只返回建议、依据与版本；执行层是 `services.py` 加独立的模拟财务服务，负责精确金额、预算查询与幂等写回。四层之间只通过明确接口交互：前端不接触工具密钥与业务规则，认知层不决定是否跳过硬规则，执行层不解析用户输入，数据层只做持久化。

几个关键取舍值得记录。第一，金额一律用 `Decimal` 与十进制字符串传输，禁止二进制浮点，因为报销金额一旦出现 0.01 的误差，后面所有阈值判断都不可信。第二，时间统一用 UTC ISO 字符串存储，前端按 Asia/Shanghai 展示，避免 SQLite 与 PostgreSQL 在时区语义上的不一致。第三，执行采用同步单进程而不是消息队列：六天周期内可演示、可调试的价值高于吞吐量，代价是不能多 worker、多副本，这条限制被明确写进文档而不是隐藏。第四，模拟财务服务独立进程、独立库、独立密钥，用来模拟真实外部系统的边界，这样工具鉴权、超时、幂等写回这些集成问题才会真实暴露。第五，认证采用 HTTP Basic 演示账号并只绑定本机，真实部署必须替换，这一点不美化。

## 四、数据库设计与演进

数据层最初用一张 `tasks` 表加六组 JSON 列（`payload`、`result`、`citations`、`logs`、`events`、`approvals`）快速联调，字段语义在 `docs/DATA-DESIGN.md` 里逐列固定：金额是字符串、`confirmed` 必须为 true、人工补充依据记为 `MANUAL` 条款、工具日志必须成对记录请求与结果且密钥不入库。幂等性靠 `(owner, request_key)` 唯一约束兜底，进程锁只用于减少冲突；PostgreSQL 上审批再加 `SELECT ... FOR UPDATE` 行锁。

进入 D2 后，周勃引入了任务快照与故障恢复所需的字段，我负责把这些变更纳入数据设计与迁移方案：新增 `submission_payload`、`parse_snapshot`、`confirmations`、`amendments`、`pending_writeback`、`failure_stage` 六个列和 `parse_snapshots` 表，升级采用“检查列存在性 + 追加式 ALTER + 回填初始请求”的幂等方式，SQLite 升级前自动生成 `.bak` 备份，旧记录只标注 `legacy_backfill` 而不推断不存在的模型调用证据。这条“只追加、不删除、可重复执行”的原则，是我在评审时坚持的：演示数据可以重置，但任何人都不能靠删表来绕过升级。

到 D5 我又补了一张 `parse_snapshots` 的完整字段表（`id`、`owner`、`description_hash`、`snapshot`、`created_at`），并把它与 `/api/parse`、`/api/invoices` 的关系写清楚：两个入口共用这张表，创建任务时用 `parse_id` 或 `invoice_id` 回传，服务端校验归属，二者互斥。

## 五、接口契约与集成

接口约定是我工作的主线。我把“校验顺序”写死：先做输入合法性与显式确认校验，再创建任务并持久化，再检索生效条款，再查询并校验预算，再执行分支判断，必要时等待人工，最后写回与展示。任何一步失败都要保留阶段信息，不能把“HTTP 200”当成“业务成功”。错误码统一为 401/403/404/409/422，幂等键 8 到 100 字符、必须含非空白字符、服务端不回传、由客户端保存复用。

认知层的集成是 D2 到 D4 的重点。`ai.py` 适配层的职责被限定为四件事：启用开关、可达性预检、枚举与格式映射、契约保持与降级留痕。其中“预检”是为了避免本地模型不可达时按 120 秒超时把 `/api/parse` 挂死；“契约保持”则是把 `mode`、`suggested_amount`、`suggested_category`、`requires_confirmation`、`message` 五个字段钉死不破坏前端，其余来源与降级信息作为增量字段追加。降级语义按 PRD 实现：模型不可用时 `mode=rule_fallback`、`requires_manual_review=true`，任务会转人工并保留制度与预算证据，绝不把降级结果当作可信数据自动通过。

D4 的 DeepSeek 联调补上了 PRD FR03 要求的两组证据：结构化报销单 8 字段零缺失（约 1.5 秒）、自由文本可提取金额与类别（约 1.1 秒）；密钥缺失时降级留痕、任务转人工。D5 我又按用户要求追加了发票 PDF 上传：用 `pypdf` 读文字层、复用同一条提取链路、结果写入解析快照、以 `invoice_id` 入任务审计，文件只在内存解析不落盘，扫描件明确拒绝。它超出了 PRD 原始范围，因此我在文档里写明了回退清单，等待产品确认。

## 六、验证体系与证据

我不相信“我手动点过了”这类结论，所以把验证做成了四个可重复的入口：`pytest`（131 项，覆盖契约、权限、边界、异常、幂等、迁移、发票与适配层）、`smoke.py`（自起自停真实 HTTP，覆盖解析快照、原子补正、初始请求重放、写回中断与 CLI 对账）、`verify_system.py`（标准端口 46 项，六个演示步骤与接口契约）、`verify_integration.py`（我写的 51 项，覆盖状态事件序列、三角色权限矩阵、解析与冲突、审批补正、指标交叉核对、凭证回溯）、`verify_restart.py`（19 项，覆盖重启续跑、幂等重放、执行中任务被标记中断、受限恢复与终态拒绝），外加发票端到端 14 项与前端构建。

D5 还完成了两件此前缺证据的事：一是在 Docker Compose + PostgreSQL 上跑通四容器（健康检查、迁移、审批、指标、发票上传），二是在**干净目录**（用 `git worktree` 导出、无 `.venv`、无 `.env`、无密钥、无 `node_modules`）独立部署候选版并从该目录跑通全部门禁。这直接支撑了“候选版可被非部署负责人独立复现”这一验收要求。

## 七、踩过的问题与修复

这个过程里我犯的错比写对的代码更值得记录。最典型的是两处编码问题：我在 `dev.ps1` 里写了中文注释，文件是无 BOM 的 UTF-8，Windows PowerShell 5.1 按 GBK 解码后把注释后的 `}` 吃掉，导致全队启动脚本报错——修法是把启动脚本注释改成纯 ASCII，并把这个坑写进文档；另一处是我给 Docker 写 `daemon.json` 时用了带 BOM 的编码，Docker 报 `invalid character 'ï'` 直接起不来，修法是改用 UTF-8 无 BOM 写入并保留备份。这两次都说明一件事：跨平台、跨工具的默认编码不能想当然。

其余问题包括：Docker Hub 拉取超时（用 `registry-mirrors` 解决，并记录了国内镜像站会变化）、docker 全路径调用时凭证助手不在 PATH、端口 10048 被残留进程占用、`verify_system.py` 里“完成数等于总数”的干净库假设（已在文档标注并改用交叉核对）、DeepSeek 返回的实际模型名与配置写的名字不一致（配置与评测统一为 `deepseek-flash`）、以及远端合并时 `.gitignore`/`INTEGRATION.md`/`App.vue` 的三处冲突（我保留了双方的产物并重新编号章节，`App.vue` 以远端版本为基线重新补回发票 UI）。

## 八、协作与流程

团队用每日日志、共享看板与 PR 合并推进。我按日期维护自己的开发日志，每天记录实际完成项、验证数字、发现的问题和阻塞，历史结论需要纠正时追加更正而不是覆盖。接口变更固定顺序是 `schemas.py → docs/API.md → frontend/src/api.ts → 测试 → 现场脚本`，这条顺序被写进文档，避免出现“代码改了文档没改、测试还按旧口径”的分叉。密钥治理也按这个思路：`dsapi.txt`、`.env` 与私有模型覆盖配置全部进 `.gitignore`，我用 `git check-ignore`、全量文件扫描和 48 个历史提交的实际密钥串扫描三重确认没有泄漏，并把“各人如何用自己的 API”写成可照抄的配置说明。

## 九、不足与反思

第一，我对平台差异的预判不够，两次编码事故都是本可避免的工程习惯问题，教训是“改脚本前先看目标解释器版本”。第二，验证脚本里曾隐含“干净库”假设，虽然及时改为交叉核对，但说明写断言时容易把当时的条件当成前提。第三，模型通道的真实调用证据落后于计划（D3 应完成，实际在 D4 补上），根因是资源（密钥/模型环境）依赖外部确认，我没有更早把风险升级。第四，发票上传属于范围外追加，虽然做了实现和回退方案，但它确实增加了候选版的不确定性与文档维护成本。第五，个人总结与文档、日志之间的口径维护成本偏高，理想做法是把关键数字（门禁项数、版本号）收敛到单一来源，避免多处手抄。

## 十、下一步

D6 的核心是“提交与现场保障”：核对代码与部署包、备份可运行版本、确认依赖与初始化说明齐全、现场按 `docs/RELEASE.md` 的门禁再跑一遍四类演示与指标、准备好数据重置与故障处置（中断任务用受限 CLI、模型不可用走降级并如实说明）。答辩时我准备重点讲三件事：架构为什么这样切分（分层边界与硬规则归位）、数据和接口为什么这样约定（金额精度、幂等、事件序列、任务编号贯穿）、以及证据在哪里（哪条命令、哪个脚本、哪份文档对应哪个验收项）。这套系统的价值不在于“自动化了多少”，而在于它把每一次自动判断都变成了可以复核、可以追溯、可以安全停机的过程，这也是我这次实训最大的收获。
