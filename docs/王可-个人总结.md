# 面向中小企业的数字员工系统设计与实现——个人总结

## 一、项目背景与个人职责

本次实训项目围绕中小企业费用报销初审场景，目标是设计并实现一个能够协助员工提交报销、自动提取字段、检索企业制度、查询预算、生成初审意见并在必要时转人工审批的数字员工系统。与普通表单系统相比，这个系统不仅要“接收数据”，还要让自动处理过程可解释、可追溯，并在信息不足、金额超限、模型不可用或制度没有依据时安全地停下来。项目周期紧凑，团队需要在六个工作日内完成需求、开发、集成、测试、部署和答辩准备，因此每个人都必须保证自己模块既能独立验证，又能顺利接入完整链路。

我在团队中负责员工端前端开发，具体范围包括报销提交、任务列表、任务详情以及初审和最终结果展示。员工端是业务链路的起点，也是普通员工观察数字员工处理过程的主要窗口。我的工作不只是实现几个页面，还包括统一前后端字段、梳理状态含义、处理输入错误和网络异常、避免重复提交、展示制度依据，并准备模块文档、测试证据和答辩讲解。拿到团队仓库后，我在既有 Vue 3、TypeScript 与 FastAPI 技术栈上完成界面重构，复用真实认证、任务、解析和指标接口，同时保留原有审批人和管理员能力，避免员工端改造破坏其他成员的工作。

## 二、需求理解与界面方案

我首先把员工端需求拆成四个核心问题：员工怎样准确提交一笔报销；提交后怎样找到自己的任务；怎样理解数字员工给出的初审意见；当流程不能自动继续时，员工应该做什么。围绕这四个问题，我设计了工作概览、发起报销、我的任务和任务详情四个主要视图。工作概览展示累计提交、待审批、处理中和已完成数量，同时列出最近任务，使用户登录后能快速判断是否有待办。发起报销页面将项目、类别、金额、日期和说明集中在结构清晰的基本信息区，并将字段提取建议作为提交前的独立核对步骤。任务列表提供编号、项目或说明搜索以及状态筛选，适合任务数量增加后的查询。任务详情集中展示报销字段、初审结论、制度条款和执行时间线，使用户不仅看到“通过或拒绝”，还能看到依据与过程。

在视觉方案上，我选择稳重的深绿色作为主色，原因是费用与审批类系统需要传达可靠、克制和明确的感觉。不同状态采用文字、圆点和浅色背景共同表达，避免只用颜色区分。页面在桌面端使用侧边导航，在窄屏下切换为可展开导航；表单从双列变为单列，详情页从主栏加侧栏变为上下排列。这样既能满足答辩现场的大屏演示，也能在普通笔记本和手机宽度下正常使用。界面中的“演示数据模式”始终可见，明确告诉验收者当前数据来源，避免把模拟接口误当作真实集成结果。

## 三、核心实现与技术取舍

为了降低团队集成成本，我复用了 `frontend/src/api.ts` 的统一请求方法。页面通过 `/api/me` 获取身份，通过 `/api/parse` 获取字段提取建议，通过 `/api/tasks` 查询和创建任务，并按角色访问审批或指标接口。请求统一携带 Basic 演示认证，创建任务额外携带 `Idempotency-Key`。任务状态严格采用后端约定的 queued、running、awaiting_approval、writing_back、succeeded、rejected 和 failed 七个枚举，再由前端映射为中文标签，避免前后端对状态含义产生分歧。

提交表单字段严格遵循后端 `ClaimInput`：项目编号、报销类别、金额、费用日期、报销说明和确认标记。验证规则不仅检查是否为空，还检查金额须在 0.01 至 5000 元之间、费用日期不能晚于当前日期、说明至少十个字。这样可以在请求发出前拦截明显错误，减少后端压力。用户输入时，未提交内容自动保存为浏览器草稿，页面刷新后可恢复。提交开始后按钮立即禁用并显示处理中状态，后端同时使用幂等键控制重复创建，从前后两层避免连续点击生成多个任务。

团队规则基线实现了多条关键分支：P001 中不超过 1000 元且有制度依据的费用可自动完成初审；超过 1000 元的任务进入人工审批；P002 预算不足时给出拒绝结果；“其他”类别因为缺少适用制度而转人工，并要求审批通过时补充人工依据。预置的审批接口还能演示通过后续跑、拒绝终止、重复审批冲突与写回失败。员工端完整展示这些状态、原因、依据和时间线，没有在浏览器中重复实现后端业务规则。

## 四、稳定性、安全性与可维护性

费用报销系统涉及金额和项目归属，前端不能只追求“看起来能用”。我重点处理了几类容易在演示中暴露的问题。第一类是重复操作：提交期间锁定按钮，后端幂等标识与当前表单内容绑定。第二类是失败恢复：API 异常以明确消息提示，不清空用户表单；未提交草稿保存在本地，刷新不会丢失。第三类是空状态：没有任务或筛选无结果时，页面显示原因和下一步提示，而不是留下空白区域。第四类是数据展示安全：Vue 模板默认对插值文本转义，不使用 `v-html` 拼接任务内容。第五类是配置安全：浏览器只持有课程演示身份，不接触模拟财务服务的工具密钥。

为了方便维护，我没有把所有逻辑混在一个页面事件中，而是区分路由切换、列表渲染、详情渲染、表单验证、草稿处理和 API 访问。README 中记录了运行命令、演示路径、接口清单、字段结构、状态含义和已知边界。自动测试会检查核心页面入口、接口字段、关键状态、异常处理标记以及是否误写密钥。虽然测试不能代替浏览器端端到端测试，但能够在修改后快速发现核心结构被破坏的问题。

## 五、测试过程与问题反思

我的测试思路是从正常流程、异常输入、边界条件和恢复能力四个方向展开。正常流程包括小额报销自动通过、大额报销进入审批、列表查询和详情展示；异常输入包括必填缺失、金额为零、金额超限、未来日期和说明过短；边界流程包括无制度依据、预算不足、审批拒绝和接口失败；恢复能力包括连续点击、页面刷新和筛选空结果。每个场景都写明输入、预期状态和可观察结果，便于测试负责人独立复现。

实现中我认识到，前端与 AI 系统的结合并不是简单展示一段模型文本。模型输出必须落到稳定的数据结构中，例如结论摘要、风险等级、条款编号、制度版本和时间线节点；缺少依据时必须明确提示，不能生成看似合理的制度内容。页面也不能把 AI 意见写成最终决定，因而在详情侧栏明确说明初审意见仅作为审批辅助，最终结果以人工审批为准。对于金额阈值和制度版本，前端只负责展示，不应成为真实业务规则的唯一执行位置。演示模式中的判断只是用于离线演示，生产环境必须以服务端状态机和权限校验为准。

目前仍有几项需要在后续迭代中完成。真实票据上传尚未进入当前接口契约；HTTP Basic 仅适合本地课程演示，正式部署要替换为安全认证；审批通过后的实时刷新目前依赖手动刷新，后续可使用轮询、SSE 或 WebSocket；失败状态的重试权限也需要产品和后端共同定义。我在代码和文档中明确标出这些边界，没有用静态假数据冒充已完成的真实接口。后续联调时，我会重点验证大额审批、拒绝、预算不足与工具异常分支。

## 六、协作体会与个人收获

这个项目让我更清楚地认识到，短周期团队开发中，接口约定和验收证据与编码本身同样重要。员工端处在产品、后端、AI 和测试的交叉位置：字段需要与后端一致，条款结构需要与 AI 输出一致，状态变化需要与审批台一致，异常表现还要能被测试人员复现。如果每个模块只按自己的理解开发，最后一天才联调，极易出现字段命名、状态含义和错误处理不一致的问题。因此我在实现中尽量把约定写成表格和稳定枚举，并保留模拟与真实 API 的切换能力，使其他成员可以在接口未完成时理解前端需要什么，在接口完成后快速替换数据来源。

我也更加重视“可解释的交互”。以往做前端时，我可能更关注布局、颜色和按钮是否可点击；这次面对数字员工场景，我需要站在用户角度回答：系统为什么要求人工审批，引用的是哪一条制度，当前在等待谁，拒绝后是否还会继续执行。只有把这些信息清楚呈现，AI 能力才真正成为业务工具，而不是一个不可验证的黑盒。时间线、制度版本、风险提示和下一步操作都是围绕这一目标设计的。

在工程能力方面，我巩固了模块化数据访问、响应式布局、表单状态管理、错误恢复、前后端契约和类型检查等实践。更重要的是，我学会先阅读团队既有架构和接口约定，再在真实代码基础上扩展，不为同一业务另造一套不兼容实现；对于暂未支持的票据上传和实时推送，则明确能力边界。这样的交付比单纯提供几张静态截图更可信，也更方便团队继续集成。

## 七、后续计划

在后续工作中，我将根据团队真实接口完成四项核验。第一，使用统一账号登录后提交报销，确认任务编号贯穿页面、数据库、AI 日志和审批台；第二，验证普通金额、大额审批、拒绝和异常转人工四类演示脚本，确保状态和结果一致；第三，与测试负责人共同执行重复提交、接口超时、权限错误和页面刷新用例，保存截图与缺陷记录；第四，在候选版本上按 README 独立部署，检查无个人密钥、无硬编码地址、无未说明的假数据。答辩时，我将重点讲清员工端的业务价值、API 适配设计、异常处理和能力边界，并用一条完整任务演示从提交到结果追踪的全过程。

总体而言，我完成的不只是费用报销页面，而是数字员工与普通员工之间的一套可信交互界面。它让输入更规范，让自动初审结论有依据，让等待与异常状态可见，也为人工审批保留清晰边界。通过本次实训，我对面向业务场景的前端设计、AI 输出的结构化呈现以及团队协作中的可验收交付有了更完整的理解。
