## 二、当日结论

PRD FR03（P0）要求的两组证据——**至少一组真实模型调用成功证据**与**一组服务不可用降级证据**——已具备，且两者都在业务接口层验证，而非只在独立模块内验证。

## 三、发现与处置

- 多实例启动时曾遇到旧进程占用 8000、新进程静默失败，导致 `/health` 显示 `ai_enabled=false` 却仍返回 200；已改为验证前先清理残留监听，并把 `/health` 的 `ai_enabled`/`version` 作为第一道核对。
- 探测调用返回的实际模型名为 `deepseek-flash`，配置中为 `deepseek-chat`，属服务端别名映射；冻结配置版本时以实际返回模型名为准记录。
- `verify_system.py` 的「指标已完成数与任务总数一致」隐含干净库假设，在带历史任务的库上会失败（产品已指派修复）；本轮改为在重置后的库上执行，并用 `verify_integration.py` 的指标交叉核对作为补充。

## 补充（2026-11-10 晚间）：发票 PDF 上传与字段抽取

用户要求员工可直接上传电子发票 PDF。已实现并验证，当日追加记录。

### 变更内容

1. **后端新增抽取模块** `backend/app/invoices.py`：用 `pypdf` 读取 PDF 文字层，做规范化、页数/字符数统计与确定性提示（发票号、日期、抬头）；文件只在内存解析，不落盘。错误分类：空文件、非 PDF、超 5 MB、加密、损坏、无文字层（扫描件）。
2. **新增接口** `POST /api/invoices`（employee，multipart）：抽取文本后复用 `/api/parse` 的字段提取链路，返回与 `/api/parse` 同构的结果，另加 `invoice_id` 与 `invoice`（文件名、页数、字符数、原文摘要、提示）。结果写入 `parse_snapshots` 供溯源。
3. **创建请求新增可选 `invoice_id`**：与 `parse_id` 互斥；携带时加载发票快照作为任务 `parse_snapshot`，并随 `submission_payload` 入档。类别/金额冲突仍走既有 `conflict_acknowledged` 闸门。
4. **前端**：`api.ts` 增加 `uploadInvoice()` 与发票类型；`App.vue` 的「02 发票与字段核对」增加 PDF 上传、页数/字符数/原文摘要展示、发票号提示与「把抽取结果填入表单」按钮；提交时优先携带 `invoice_id`。
5. **依赖**：`backend/requirements.txt` / `.in` 增加 `pypdf==7.0.0`、`python-multipart==0.0.33`。

### 边界与待决

- 只支持带文字层的电子发票；扫描件/图片型 PDF 明确拒绝并提示手工填写（OCR、发票验真按 PRD 不在本期范围）。
- 这份能力超出了 PRD V0.3 的原始范围，属用户要求的 D4 追加变更：**需产品在范围内确认并同步需求与看板**；若不保留，可按 `docs/INTEGRATION.md` 第十一节列出的四类改动整体回退。
- 中文发票的抽取质量（字体/ToUnicode 映射）需用真实票据核对一次，接口返回的 `text_preview` 可直接判断是否乱码。
